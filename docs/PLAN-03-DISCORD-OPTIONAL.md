# 계획 03 — 디스코드를 선택 기능으로

작성: 2026-08-16 · 상태: **계획. 구현 없음.**
선행: [PLAN-01](PLAN-01-SESSION-CORE.md) 전 단계, [PLAN-02](PLAN-02-CRATE-SPLIT.md) 6단계

> "디코랑도 아예 벗어나고"

---

## 목표

**디스코드 계정 없이 방을 만들고, 초대하고, 같이 들을 수 있다.
디스코드는 켜면 좋은 기능이 되고, 없어도 서비스가 돈다.**

지금은 반대다. **디스코드 봇 토큰이 없으면 프로세스가 아예 안 뜬다**
(`src/config.rs:119-124`).

## 정직한 규모 측정

이건 앞의 계획들보다 훨씬 크다. 숫자로 먼저 본다.

| 측정 | 값 |
|---|---|
| `guild_id` 등장 횟수 | **2,164** (`user_id` 는 716) |
| `guild_id: u64` 선언 | **306**. 뉴타입 0개, 방/공간 추상 **0개** |
| `guild_id` 를 가진 DB 테이블 | **39개 중 28개** |
| 길드 경로 아래 있는 웹 라우트 | **79개 중 61개** (`/music/api/guilds/{guild_id}/...`) |
| serenity·songbird 를 import 하는 파일 | 34개 중 **10개** |
| `MemberContext` 필드 | 4개 중 **3개가 디스코드 파생** |
| 권한 규칙 변종 | 5개 중 **3개가 디스코드 고유** (`SameVoiceChannel`·`ConfiguredRole`·`Administrator`) |

> **`guild_id` 는 이 저장소에서 사실상 "방 번호" 로 쓰이고 있다.**
> 이름만 디스코드일 뿐, 의미는 이미 방이다. 그게 이 계획을 가능하게 만든다.

### 이미 디스코드를 모르는 것 (그대로 살아남는다)

검색·리졸버·yt-dlp·캐시·대기열 정렬(`ranking.rs`)·자동재생·차트·TJ 노래방 차트·가사·
통계·채팅·건의함·감사 로그·정지 처분·개인 설정 — 전부 serenity import 0.

프론트엔드는 **구조적으로는** 디스코드를 모른다 — `guildId` 를 불투명한 경로 조각으로만
쓴다(`portal.js` 에 4곳).

> **다만 "디스코드 0회" 는 틀렸다.** 초안에 그렇게 적었는데 교차검증이 반박했고,
> 직접 세어 보니 자산 전체에 `discord` 가 **28회** 나온다 (`console.js` 15,
> `portal.js` 13). 전부 **사람에게 보여 주는 문구**다. 예:
>
> ```js
> // portal.js:5407
> setWebNote('이 곡은 웹에서 재생할 수 없어요. Discord로 들어 주세요.');
> ```
>
> 토큰 없는 모드에서 이 문장은 **거짓 안내**가 된다 — 들어갈 디스코드가 없다.
> `console.js` 쪽 15회는 권한 규칙 설명("같은 음성 채널" 등)이라 3단계에서 같이 바뀐다.

→ **화면은 배선을 고칠 게 거의 없다. 대신 문구 28곳을 손봐야 한다.**
구조 변경보다 훨씬 싼 일이지만, 빼먹으면 사용자가 없는 기능을 안내받는다.

## 벽 넷

### 벽 1. 방이 없다 — `guild_id` 가 방이다

방/공간 추상이 저장소에 **하나도 없다**. `WatchParty` 조차 `HashMap<u64(guild), _>` 로
길드에 매달려 있다(`src/web/mod.rs:206`).

바꿔 말하면 **방 개념을 새로 만드는 게 아니라, 이미 있는 것에 이름을 주는 일**이다.

### 벽 2. 신원이 스노플레이크다

- OAuth 콜백이 `discord.com/api/v10/users/@me` 를 부르고 `user.id.parse::<u64>()`
  (`src/web/remote.rs:3138`·`:3160`)
- 아바타가 `cdn.discordapp.com/avatars/{user_id}/...` (`:3165`)
- 세션 테이블 `remote_web_sessions.user_id INTEGER` (`src/remote/store.rs:199-213`)
- 봇 주인이 디스코드 유저 id 목록 (`src/app.rs:137-138`)

로컬 계정 테이블은 **없다.** `MUSICBOT_DEV_LOGIN` 경로가 있지만
(`src/web/remote.rs:3229-3297`, 루프백 전용) 그건 **디스코드 모양의 세션을 위조하는
시험 장치**이지 로컬 계정이 아니다 — 길드를 `owner: true, permissions: ADMINISTRATOR`
로 지어낸다.

### 벽 3. 권한이 디스코드 역할과 음성 채널이다

```rust
// src/remote/models.rs:1817-1825
pub enum PermissionRule {
    GuildMember, SameVoiceChannel, ConfiguredRole, Administrator, Disabled,
}
```

`RemoteGuildSettings` 에 `PermissionRule` 필드가 **10개**, 거기에 딸린 역할 id 목록이
3종(`configured_role_ids`·`rule_role_ids`·`manager_role_ids`) — 전부 디스코드 스노플레이크.

그리고 `MemberContext`(`src/web/remote.rs:370-381`)의 네 필드 중 셋이 디스코드 파생이다:
`is_admin`·`same_voice_channel`·`bot_in_voice`·`role_ids`.

다행히 **평가 함수는 하나다** — `permission_allowed`(`src/web/remote.rs:1547-1565`).
디스코드 명령 계층도 이걸 부른다(`src/commands/handlers.rs:11`). 갈아 끼울 자리가
한 군데라는 뜻이다.

### 벽 4. "누가 여기 있나" 가 두 출처의 합이다

`build_presence`(`src/web/remote.rs:2073-2128`)가 네 통을 만든다:

| 통 | 출처 |
|---|---|
| `listening` | 디스코드 음성 상태 (봇이 있는 채널) |
| `inOtherVoice` | 디스코드 음성 상태 (다른 채널) |
| `viewing` | **웹소켓** |
| `online` | 디스코드 게이트웨이 presence |

넷 중 하나만 디스코드와 무관하다. 그리고 스킵 투표 정족수가 **두 통을 다 쓴다**
(`skip_quorum`, `:2386-2440`).

## 설계 — 뉴타입 하나로 시작한다

```rust
// mc-domain
pub struct RoomId(pub u64);

pub enum RoomKind {
    Discord { guild_id: u64 },   // 지금 있는 전부. id 는 길드 id 그대로.
    Standalone,                  // 새로 생기는 것
}
```

**핵심: 기존 방의 `RoomId` 는 길드 id 를 그대로 쓴다.** 그러면 DB 마이그레이션이
"컬럼 이름 바꾸기" 조차 필요 없다 — 28개 테이블의 `guild_id` 컬럼이 그대로 `RoomId` 를
담는다. **데이터 이전이 0이다.**

새로 만드는 독립 방은 스노플레이크와 안 겹치는 범위에서 발급한다.

같은 방식으로:

```rust
pub struct AccountId(pub u64);

pub enum Identity {
    Discord { user_id: u64 },
    Local { .. },
}
```

### 권한을 두 층으로 가른다

```
PermissionRule (지금)                →   Capability (도메인)  +  Evidence (제공자)
─────────────────────────────────────────────────────────────────────────────────
GuildMember                          →   방 구성원
SameVoiceChannel                     →   "같이 듣고 있음"      ← 디스코드 음성 OR 웹 리스너
ConfiguredRole                       →   지정된 등급           ← 디스코드 역할 OR 방 등급
Administrator                        →   방 관리자             ← 디스코드 권한 비트 OR 방 주인
Disabled                             →   그대로
```

**`SameVoiceChannel` 을 "같이 듣고 있음" 으로 재해석하는 게 핵심이다.**
그러면 웹으로만 듣는 사람도 그 조건을 만족할 수 있고, 지금 이미 있는
`web_listeners`(`src/web/mod.rs:196`)가 그 증거가 된다.

> **지금 동작을 정확히 적어 둔다.** 초안에 "지금은 디스코드 음성만 증거로 인정한다"
> 고 썼는데 **틀렸다.** `same_voice_satisfied`(`src/web/remote.rs:1576-1588`)는
> 봇이 음성에 **없을 때** 이미 이렇게 연다:
>
> ```rust
> if member.bot_in_voice { return false; }
> !settings.require_voice_for_playback || settings.web_player_mode
> ```
>
> 즉 `web_player_mode` 가 켜져 있으면 **그 사람이 실제로 웹으로 듣고 있는지와 무관하게
> 통과한다.** 지금은 "듣고 있음" 이 아니라 "들을 수 있는 상황임" 을 보고 있다.
>
> 그래서 3단계는 **넓히는 일이 아니라 좁히면서 정확하게 만드는 일**이다 —
> `web_listeners` 에 실제로 있는 사람만 통과시킨다. **지금보다 엄격해지는 방향이라
> 기존 사용자가 못 누르게 될 수 있다.** 아래 단계에서 이 위험을 다시 다룬다.

`MemberContext` 는 필드 이름만 바뀐다: `same_voice_channel` → `listening_together`,
`bot_in_voice` → `room_has_output`, `role_ids` → `grant_ids`.

## 단계

### 1단계 — 이름부터 (동작 변경 0)

`RoomId`·`AccountId` 뉴타입을 도입하고 `u64` 를 대체한다. **DB 도 라우트도 안 바꾼다.**
306개 선언을 바꾸는 기계적인 작업이지만, 이게 끝나면 컴파일러가 방 id 와 사람 id 를
헷갈리지 않게 막아 준다.

**완료조건**

- DB 스키마 버전 그대로 (v22). 운영 DB 사본 마이그레이션 dry-run 이 **아무것도 안 한다**
- 웹 라우트 경로 문자열 79개 그대로
- 주요 응답 JSON 이 **바이트 단위로 같다**

**응답 비교만으로는 부족하다** — 교차검증 지적대로 아래는 컴파일도 통과하고 JSON 도
같은데 런타임에만 깨진다. 별도로 확인한다:

| # | 확인 | 방법 |
|---|---|---|
| 1 | axum 경로 역직렬화 | `Path<RoomId>` 가 기존 `Path<u64>` 와 같은 문자열을 받는다 |
| 2 | SQLite 왕복 | `RoomId` 저장 → 읽기 → 값 동일 (`rusqlite` `ToSql`/`FromSql` 구현) |
| 3 | 최대 스노플레이크 | `u64::MAX` 에 가까운 id 가 **SQLite `INTEGER`(i64) 에서 안 깨진다** ← 지금도 잠재 문제. 이 단계에서 확인만 하고, 깨지면 별도 항목으로 뺀다 |
| 4 | 종류 혼동 | `AccountId` 를 방 자리에 넣으면 **컴파일 실패** (이게 뉴타입의 전부다) |

### 2단계 — 권한을 능력으로 (동작 변경 0)

`PermissionRule` → `Capability` + `Evidence`. 지금 규칙이 그대로 매핑되는지가 완료조건.

**완료조건 — 전수표로 판정한다**

`(규칙 5종) × (봇 음성 유무) × (같은 채널 여부) × (require_voice_for_playback) ×
(web_player_mode) × (관리자 여부) × (역할 보유 여부)` 조합을 전부 돌려
**기존 `permission_allowed` 와 새 평가기의 판정이 100% 일치**해야 한다.

그리고 판정을 쓰는 곳이 두 곳이 아니다. 교차검증이 찾아 준 **전체 호출부**:

| 자리 | 파일 |
|---|---|
| 웹 조작 인가 | `remote.rs:AuthContext::allows` |
| 권한 JSON 응답 | `remote.rs:permissions_json` |
| 역할 미리보기 | `remote.rs:admin_role_view` |
| 관리자 권한 미리보기 | `remote.rs:admin_permission_preview` |
| 디스코드 명령 | `commands/handlers.rs:11` (import), `ensure_autoplay_allowed` |

- 위 다섯 곳 전부 새 평가기를 쓴다
- **기존 설정 JSON 이 그대로 읽힌다** — `RemoteGuildSettings` 직렬화 형식 무변경
  (운영 DB 사본으로 왕복 시험: 읽기 → 쓰기 → 바이트 비교)

### 3단계 — "같이 듣고 있음" 을 실제 청취로 (첫 동작 변경)

`web_listeners` 에 실제로 있는 사람만 통과시킨다.
**위 설계 절에 적었듯 이건 지금보다 엄격해지는 방향이다.**

| 주의 |
|---|
| 기본값은 **지금 동작 그대로.** 새 설정을 켜야 엄격해진다 |
| 새 설정 이름·기본값을 이 단계에서 확정한다 (`require_actual_listening`, 기본 `false`) |
| 지금 "음성 채널에 있어야 스킵 가능" 을 **의도적으로** 쓰는 서버가 있다 |

**완료조건 — 8행 전수표**

| # | 봇 음성 | 나 음성 | web_player_mode | 웹으로 듣는 중 | 새 설정 | 기대 |
|---|---|---|---|---|---|---|
| 1 | 있음 | 같은 채널 | — | — | off | 통과 |
| 2 | 있음 | 다른 채널 | — | — | off | 거절 |
| 3 | 없음 | — | on | 예 | off | 통과 |
| 4 | 없음 | — | on | **아니오** | off | **통과** (지금 동작) |
| 5 | 없음 | — | on | 예 | **on** | 통과 |
| 6 | 없음 | — | on | **아니오** | **on** | **거절** (새 동작) |
| 7 | 없음 | — | off | — | off | `require_voice_for_playback` 값을 따른다 |
| 8 | 있음 | 다른 채널 | on | 예 | on | 거절 (봇이 있으면 음성이 우선) |

4행과 6행의 차이 하나가 이 단계의 전부다.

### 4단계 — 프로세스가 토큰 없이 뜬다

`src/config.rs:119-124` 의 하드 실패를 없앤다. 토큰이 없으면 `mc-discord` 를 안 띄우고
웹만 돈다.

**토큰만 없앤다고 되는 게 아니다.** 교차검증이 찾아 준, 디스코드 캐시가 없으면
막히는 경로들:

| 자리 | 지금 동작 | 해야 할 일 |
|---|---|---|
| `remote.rs:authorize` | 디스코드 캐시가 없으면 비개발자 요청을 **거절** | 방 소속을 캐시가 아닌 곳에서 판정 |
| `remote.rs:portal_home` | 길드 목록이 OAuth 응답에서 온다 → **빈 목록** | 방 목록을 로컬에서 |
| `events.rs:Handler::ready` | **재시작 이어듣기가 여기서만 불린다** | 토큰 없이도 부팅 시 불리게 |
| 역할 조회 실패 시 503 | `remote.rs:429-434` "Discord에서 내 역할을 확인하지 못했어요" | 토큰 없는 모드에선 이 경로 자체가 없어야 |

> 세 번째가 특히 중요하다 — [PLAN-04](PLAN-04-ZERO-DOWNTIME.md) 에서 확인한
> **부팅 시 유일한 `sync_guild` 호출**이 디스코드 `ready` 안에 있다. 토큰이 없으면
> 그 훅이 영원히 안 불린다.

**완료조건**

| # | 시나리오 | 기대 |
|---|---|---|
| 1 | 토큰 없이 기동 | 프로세스가 뜬다. `/healthz` 200 |
| 2 | 토큰 없이 로그인 | 방 목록이 **비어 있지 않다** |
| 3 | 토큰 없이 조작 | 검색·담기·스킵·시크·볼륨이 **200** (지금은 `authorize` 에서 403) |
| 4 | 토큰 없이 브라우저 2개로 같이 듣기 | 두 창의 위치 차 **2초 이내** (`WEB_SYNC_GAP`) |
| 5 | 토큰 없이 재시작 | 껐을 때 위치에서 이어진다 (PLAN-04 1단계 필요) |
| 6 | 토큰 **있을 때** | 위 3의 응답과 DB 상태가 **변경 전과 동일** |
| 7 | 숨어야 할 화면 | 음성 바인딩 · 역할 권한 설정 · 인텐트 상태 · 알림 채널 · 빈 채널 정책 · 봇 아바타 — **6개가 안 보인다.** 열어도 500 이 아니라 안내 |

> 이 단계에서 [PLAN-01](PLAN-01-SESSION-CORE.md) 이 필수인 이유가 드러난다.
> 디스코드가 없으면 시각표를 만들 수 있는 건 가상 갈래뿐이다. 시각표가 진실이 아니면
> **토큰 없는 모드는 위치를 아무도 모르는 상태가 된다.**

### 5단계 — 로컬 계정과 독립 방

여기서부터 진짜 새 기능이다.

**먼저 결정할 것 — 이게 안 정해지면 완료조건을 못 쓴다.**

| 결정 | 선택지 | 잠정 |
|---|---|---|
| 인증 방식 | 비밀번호 / 매직 링크 / 패스키 | **매직 링크.** 비밀번호는 해시·재설정·유출 대응이 통째로 새 책임이다. 메일 발송 하나만 붙이면 되는 쪽이 싸다 |
| `RoomKind`·`Identity` 영속화 | 새 테이블 / 기존 테이블에 컬럼 | 새 테이블 (`rooms`, `accounts`). 28개 테이블의 `guild_id` 컬럼은 그대로 `RoomId` 를 담는다 |
| 독립 id 발급 범위 | — | 스노플레이크는 2^63 미만이므로 독립 id 는 그 위에서 발급. **단 SQLite `INTEGER` 는 i64 라 2^63 이상이 음수가 된다** — 1단계 확인 #3 과 같은 문제다. 확인 후 범위를 정한다 |

| 할 일 |
|---|
| 로컬 계정 (`Identity::Local`) + 매직 링크 |
| 방 만들기 / 초대 링크 (`RoomKind::Standalone`) |
| 방 등급 (주인·관리자·구성원·손님) → 3단계의 `Evidence` 자리에 |
| 디스코드 계정 **연결** — 로그인 수단이 아니라 부가 연결 |

**완료조건**

| # | 시나리오 | 기대 |
|---|---|---|
| 1 | 메일로 계정 만들기 | 로그인됨. `accounts` 행 +1 |
| 2 | 방 만들기 | `rooms` 행 +1, 만든 사람이 주인 |
| 3 | 초대 링크로 다른 사람 입장 | 구성원으로 들어옴. **링크 재사용이 정책대로** (1회용이면 두 번째 거절) |
| 4 | 등급별 조작 | 3단계 전수표가 방 등급 증거로도 같은 판정 |
| 5 | 디스코드 계정 연결 | 같은 사람으로 인식. 계정 **2개가 안 생긴다** |
| 6 | 재시작 | 계정·방·등급이 전부 복원 |
| 7 | 만료된 매직 링크 | 거절. 오류 메시지가 사람 말 |

**여기서 멈춰도 된다.** 4단계까지만 해도 "디스코드 없이도 서비스가 돈다" 는 사실이 된다.
5단계는 그 위에 사람을 받는 일이라 성격이 다르다 — 계정을 받는 순간 개인정보·메일 발송·
비밀번호 분실 대응이 전부 새 책임으로 들어온다.

## 디스코드에만 남는 것 (없애지 않는다)

이건 없애야 할 부채가 아니라 **디스코드를 켰을 때의 이득**이다.

슬래시 명령 27개 · 임베드/버튼 카드 · 음성 채널 바인딩 · 빈 채널 자동 퇴장 ·
역할 기반 권한 · 게이트웨이 인텐트 상태 표시 · 알림 채널 게시 · 봇 아바타 ·
`/리모컨` 링크 · **그리고 실제로 음성 채널에서 소리가 나는 것.**

마지막 것이 제일 중요하다. **디스코드 없이 돌 때는 각자 브라우저에서 소리가 난다.**
"다 같이 한 스피커로" 가 아니라 "각자 기기에서 같은 지점" 이다. 그 차이를 화면이
정직하게 말해야 한다.
