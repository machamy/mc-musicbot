# 계획 04 — 노래 안 끊고 배포하기

작성: 2026-08-16 · 상태: **계획. 구현 없음.** · 선행 조건 없음 (제일 먼저 해도 된다)

> "코어, 재생기, 디스코드봇, 웹서버 이렇게 네 개로 프로그램 나눠 버리면
> 노래 무중단으로 웹 업데이트 가능할 거 같은데"

결론부터. **넷 중 둘은 나눌 수 있는 물건이 아니고, 나머지 하나는 값어치가 있지만
지금 제일 급한 문제가 아니다.** 급한 건 따로 있고, 그건 반나절짜리다.

---

## 0. 먼저 — 이미 만들어 둔 §24 가 한 번도 안 돌았다

`src/shutdown.rs` 는 "종료 신호를 받으면 재생 위치를 적어 두고, 다음 기동에서 그 자리부터
잇는다"를 구현해 놨다. 그런데 **운영 호스트 로그 전체에서 `Shutdown` 카테고리가 0줄이다.**

`src/logging.rs:73-81` 은 줄마다 파일을 열고 쓰고 닫는 **동기 기록**이다. 버퍼에 남아
날아간 게 아니라 **진짜로 한 번도 안 돈 것**이다.

### 왜 안 도는가

| 자리 | 코드 | 결과 |
|---|---|---|
| `scripts/Deploy-Seamless.ps1:113` | `$p.CloseMainWindow()` | 콘솔 앱이라 안 먹는다. 주석 `:110` 에 이미 그 걱정이 적혀 있다 |
| `scripts/Deploy-Seamless.ps1:119` | 8초 뒤 `Stop-Process -Force` | `TerminateProcess`. 콘솔 제어 이벤트가 **안 간다** |
| `scripts/STOP-MK2.cmd:2` | `taskkill /im ... /f` | 같음 |

`src/shutdown.rs:105-118` 이 기다리는 건 `ctrl_c`·`ctrl_break`·`ctrl_close`·`ctrl_shutdown`
넷인데, 강제 종료는 그중 무엇도 아니다.

### 그래서 무슨 일이 생기나 — 이게 진짜 문제다

```
강제 종료 → drain() 안 돎 → remote_resume 행 없음
          → 다음 기동에서 take_resume() = None → continue
```

그런데 **부팅 시 `sync_guild` 를 부르는 곳은 `resume_after_restart` 안의 그 한 줄뿐이다.**

```
src/shutdown.rs:176:  app.coordinator.sync_guild(app, guild_id).await;   ← 부팅 경로는 여기 하나
```

(전체 호출부를 확인함: 나머지는 전부 명령·웹 핸들러·트랙 이벤트·음성 상태 핸들러다.)

→ **재시작하면 봇이 음성에 아예 안 들어온다.** 대기열도 `guild_states.voice_channel_id` 도
DB에 멀쩡히 남아 있는데 아무도 안 부른다. 사람이 다시 불러야 한다.

`src/shutdown.rs:7-9` 가 막으려던 증상이 *"처음부터 다시 틀거나 아예 안 들어감"* 이었다.
**그 증상이 지금 그대로 나고 있다.**

> 즉 지금 중단 시간은 "몇 초"가 아니라 **사람이 봇을 다시 부를 때까지**다.
> 4분할로 없애려는 그 중단이, 아키텍처 때문이 아니라 kill 신호가 안 가서 무한대다.

### 참고 실측

기동 → `Ready handler started` 까지 **3.3~5.6초** (운영 로그 12회, v4.14~v4.25).
신호만 제대로 가면 중단은 그 정도로 수렴한다.

## 1. 재생기와 디스코드봇은 나눌 수 있는 물건이 아니다

`src/shutdown.rs:3-5` 가 이미 답을 적어 놨다 —
*"프로세스 사이에 음성 연결을 넘기는 진짜 무중단은 불가능하다."*

실제 오디오 경로:

```
yt-dlp (자식 프로세스)              src/media/ytdlp.rs:548
  → 캐시 파일                       src/media/cache.rs:78
  → ffmpeg (자식 프로세스) pipe:1   src/player/coordinator.rs:1197-1256
  → ChildContainer → RawAdapter     src/player/coordinator.rs:948-961
  → songbird 드라이버 스레드 (20ms 페이싱 · 암호화 · DAVE) → UDP
```

**"재생기"라고 부를 만한 것은 이미 전부 프로세스 밖에 나가 있다.** 남은 건 songbird
드라이버 스레드 하나인데, 그게 곧 디스코드 음성 연결(UDP 소켓 + 암호화 세션)이다.
떼어 낼 수 없고, 떼어 봐야 소켓 쥔 쪽을 재시작하면 어차피 소리가 끊긴다.
**얻는 건 없고 20ms 페이싱에 IPC 지연만 새로 낀다.**

→ **하지 않는다.**

## 2. 웹서버 분리 — 진짜지만 지금은 아니다

### 값어치 (실측)

최근 40커밋 중 코드를 건드린 33개:

| 범위 | 커밋 | 웹서버가 따로 돌면 |
|---|---|---|
| `src/web/` 만 | **15 (45%)** | 노래 안 끊고 갱신 |
| 코어 포함 | 18 (55%) | 어차피 재시작 |
| (그중 JS/CSS만) | 6 (17%) | → 2절 "자산 오버라이드"로 더 싸게 해결 가능 |

브라우저 쪽은 이미 견딜 준비가 돼 있다 — `core.js:1042` 지수 백오프 재접속, 30초까지는
`reconnecting` 표시. §31 절대시각 동기라 웹에서 듣는 사람은 웹서버가 2초 죽었다 살아나도
소리가 안 끊긴다.

### 비용 (실측)

| 문제 | 숫자 |
|---|---|
| **명령 채널 seam 이 0개** | 저장소 전체에 재생 명령용 mpsc/enum 이 없다. 웹이 `player`/`coordinator` 메서드를 직접 `.await` 한다 — **61개 호출 지점** (`app.player` 42 + `app.coordinator` 19, `src/web/remote.rs`) |
| **양방향 결합** | 코어→웹 훅 4개 (`on_queue_sorted`·`on_restarting`·`on_chart_prefetch`·`web_listener_count`, `src/app.rs:142-154`) |
| **재생 hot path 가 웹 메모리를 읽는다** | `src/player/coordinator.rs:484-488` 이 `web_listener_count` 훅으로 `WebState::web_listeners` 를 **동기적으로** 읽는다 |
| **DB 파일이 하나** | `Db` 와 `RemoteStore` 가 같은 sqlite 에 각자 커넥션 (`src/app.rs:183`·`:190`). 프로세스가 갈리면 각자의 메모리 캐시가 안 맞는다 |
| **`src/web/remote.rs` 12,750줄** | 여기 테스트만 76개 |

느슨한 것도 있다 — 웹은 디스코드 REST 를 serenity 가 아니라 **자체 reqwest 클라이언트**로
쓰고(이미 프로세스 독립적), 봇→웹 알림이 push 가 아니라 **길드별 폴링 태스크**
(`ensure_guild_watcher`, `src/web/remote.rs:2205-2301`)라 그 방향은 이미 간접적이다.

### 그래서 순서

**프로세스를 나누기 전에 seam 을 먼저 만든다.** 61개 호출을 트레이트 하나로 모으고,
그게 in-process 구현으로 그대로 돌게 한다. 그 단계가 통과한 뒤에야 뒤쪽을 IPC 로
갈아끼우는 게 기계적인 일이 된다. seam 없이 프로세스부터 나누면 12,750줄을 눈 감고
자르는 게 된다.

그 seam 작업은 [PLAN-02-CRATE-SPLIT.md](PLAN-02-CRATE-SPLIT.md) 와 같은 일이다 —
**크레이트로 먼저 나누면 프로세스 분리는 그 뒤에 얹으면 된다.**

그리고 `web_listener_count` 는 RPC 로 만들면 안 된다. **방향을 뒤집어서** 리스너 수가
바뀔 때만 웹이 코어에 밀어 넣게 한다. 재생 판단 경로에 네트워크 왕복을 넣을 수 없다.

## 단계

### 1단계 — 종료 신호가 실제로 전달되게 한다 (반나절)

윈도우 콘솔 앱에 원격에서 Ctrl+Break 를 보내는 것은 프로세스 그룹 때문에 안 된다.
실용적인 선택지 둘:

| 방법 | 장점 | 단점 |
|---|---|---|
| **파일 신호** — `data/SHUTDOWN.request` 를 봇이 1초마다 확인 | 인증 표면 0. 배포 스크립트가 `scp` 한 번이면 끝 | 폴링 (1초에 파일 하나 stat — 무시할 만하다) |
| **HTTP 종료 엔드포인트** | 배포 스크립트가 이미 `/healthz` 를 폴링한다 | 인증이 필요하다. 리모컨은 공개 주소다 |

**파일 신호를 권한다.** 인증 실수의 여지가 없고, 신호가 안 갔는지 여부가 파일 존재로
눈에 보인다.

**경로 규약을 먼저 못 박는다.** 보내는 쪽(PowerShell)과 읽는 쪽(봇)이 같은 파일을
가리켜야 하는데, 봇의 작업 디렉터리는 실행 방식에 따라 다르다.

| 항목 | 규약 |
|---|---|
| 위치 | `Config::data_root` 아래 `SHUTDOWN.request` — DB·로그와 같은 뿌리라 이미 양쪽이 아는 유일한 절대 경로다 |
| 내용 | 요청 시각 rfc3339 한 줄 (진단용). 내용은 안 읽는다 — **존재 여부만** 본다 |
| 확인 주기 | 1초 |
| 지우는 시점 | **기동 직후 한 번** + 신호를 받아 처리한 직후 |

| 할 일 | 근거·주의 |
|---|---|
| `shutdown::watch` 의 `select!` 에 파일 감시 갈래 추가 | `src/shutdown.rs:112-117` — 기존 신호 넷은 **그대로 둔다** |
| 배포 스크립트가 강제 종료 **전에** 신호 파일을 쓰고 최대 8초 기다린다 | `scripts/Deploy-Seamless.ps1:110-119` — 강제 종료는 최후 수단으로 남긴다 |
| `STOP-MK2.cmd` 도 같은 순서로 | `scripts/STOP-MK2.cmd` |
| 봇이 기동 시 남은 신호 파일을 지운다 | 안 지우면 다음 기동에 즉시 자살한다 |

**완료조건 — 곡을 틀고 있는 길드 1개 기준**

| # | 확인 | 기대 |
|---|---|---|
| 1 | 종료 로그 | `Shutdown` 카테고리 **정확히 3줄**: "종료 신호를 받았어요" · "N초 지점을 저장했어요" · "정리를 마쳤어요" (지금은 0줄) |
| 2 | DB | `remote_resume` 에 그 길드 행이 **1개** 생긴다 |
| 3 | 재시작 후 | 봇이 **스스로 음성에 들어온다** (사람이 안 부름) |
| 4 | 이어듣기 정확도 | 껐을 때 위치와 재개 위치의 차 **10초 이내** (기동 3.3~5.6초 + drain 시간) |
| 5 | 신호가 안 갔을 때 | 8초 뒤 강제 종료. 배포가 **안 막힌다** |
| 6 | 안 틀고 있던 길드 | `clear_resume` 이 불려 옛 행이 **없다** |
| 7 | 6시간 넘은 기록 | 이어 붙이지 **않는다** (`RESUME_MAX_AGE_HOURS`) |

**반증 시험**: 신호 파일 감시 갈래를 임시로 빼고 배포 → `Shutdown` 로그가 다시 0줄이
되는지 확인. 안 되면 다른 경로가 있는 것이므로 원인을 다시 찾는다.

> 곁다리로 정리할 것: `shutdown::is_shutting_down()` (`src/shutdown.rs:37`) 은 호출부가
> 0개다. 그리고 `save_resume` 이 적는 `was_paused` 를 `resume_after_restart` 가 안 읽는다
> (`src/shutdown.rs:88` vs `:134-177`) — 일시정지 상태는 `guild_states.is_paused` 에서
> 온다. 둘 중 하나는 지워야 한다.

`include_str!` 은 폴백으로 남기고, 실행 파일 옆에 `web/` 폴더가 있으면 그쪽을 먼저 읽는다.

### 3단계 — (선택) 웹 프로세스 분리

[PLAN-02](PLAN-02-CRATE-SPLIT.md) 가 끝난 뒤에만 착수한다.

> **정정.** 초안에 "그때는 seam 이 이미 있으므로 트레이트 구현을 IPC 로 교체하는 일만
> 남는다" 고 적었는데 **틀렸다.** 교차검증 지적대로, PLAN-02 의 크레이트 경계는
> 웹의 **61개 구체 호출**(`app.player` 42 + `app.coordinator` 19)을 명령 트레이트로
> 바꾸지 않는다. 크레이트가 갈려도 웹은 여전히 `PlayerManager` 를 직접 부른다.
>
> **그 트레이트를 만드는 것이 이 단계의 3-0 이다.** PLAN-02 는 전제 조건일 뿐
> 대체재가 아니다.

**3-0. 명령 facade 를 만든다 (프로세스는 아직 하나)**

| 할 일 |
|---|
| 61개 호출을 `PlaybackControl` 트레이트 하나로 모은다 |
| in-process 구현이 지금 코드를 그대로 부른다 |
| `web_listener_count` 훅의 **방향을 뒤집는다** — 웹이 `set_listener_count(room, n)` 로 민다 |
| 이벤트 순서·재시도 규약을 정한다 (지금은 broadcast 채널이라 유실 가능) |

**완료조건**: `src/web/` 에서 `app.player`·`app.coordinator` 직접 호출이 **0회**.
동작은 전부 그대로.

**3-1. 프로세스를 뗀다**

먼저 정해야 할 것:

| 결정 | 이유 |
|---|---|
| **DB 를 누가 소유하나** | `Db`·`RemoteStore` 가 같은 파일에 각자 커넥션. 두 프로세스가 열면 WAL 다중 접근 + 메모리 캐시 8개가 갈린다. **코어가 소유하고 웹은 RPC 로 읽는 쪽**이 안전하지만 그러면 웹의 87+21 호출이 전부 RPC 가 된다 |
| **미디어 캐시 소유** | 파일은 코어가 쓴다. 웹은 조회만 |
| **IPC 장애 시** | 코어가 죽으면 웹은 무엇을 보여 주나. "연결 끊김" 화면이 필요하다 |

**여기서 잃는 것.** 웹 프로세스가 재시작하면 `WebState` 의 휘발성 상태가 사라진다 —
접속자 명단(`presence`), 웹 리스너(`web_listeners`), 같이보기 판(`watch_parties`),
스킵 투표(`skip_votes`). 전부 "접속 중에만 뜻이 있는" 것들이라 설계상 감수 가능하지만,
**같이보기 판이 사라지는 것은 사람 눈에 보인다.** DB에 넣거나, 재접속 시 클라이언트가
다시 알려 주게 해야 한다.

**완료조건**

| # | 확인 | 기대 |
|---|---|---|
| 1 | 웹 프로세스만 재시작 | **소리가 안 끊긴다** (디스코드 음성·웹 재생 둘 다) |
| 2 | 위 재시작 중 | 브라우저가 `reconnecting` 을 보이고 30초 안에 복구 |
| 3 | 코어 프로세스가 죽음 | 웹이 500 이 아니라 안내 화면 |
| 4 | 같이보기 중 웹 재시작 | 판이 복구된다 (또는 사람에게 왜 사라졌는지 알린다) |
| 5 | DB 동시 접근 | `SQLITE_BUSY` 로 인한 실패 **0회** (부하 시험 필요) |
