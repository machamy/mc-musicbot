# 자산 덮어쓰기 — 봇을 안 끄고 리모컨 화면 갈아 끼우기 (§43)

구현: `crates/mc-app/src/web/asset_override.rs` · `crates/mc-app/src/web/assets.rs`

---

## 왜 있나

최근 33커밋 중 **6개(17%)가 JS·CSS 만** 고친 것이었다. 그런데 배포 단위가 exe 하나라
그 여섯 번도 전부 봇을 껐다 켜야 했고, 그때마다 듣고 있던 사람의 노래가 끊겼다.

[PLAN-04](PLAN-04-ZERO-DOWNTIME.md) 가 없애려던 중단 중 이 몫만 먼저 없앤다.
프로세스를 쪼갤 필요가 없다 — 자산은 상태가 없고 요청마다 새로 읽히므로,
"지금 내보낼 바이트" 만 바꿔치면 끝난다.

**나머지 몫(웹서버 분리)은 여전히 계획 상태다.** 코어를 건드리는 배포는 그대로 재시작한다.

---

## 쓰는 법

데이터 루트(`.musicbot-data` 또는 `dataRoot` 설정값) 밑에 폴더를 만들고 파일을 떨어뜨린다.

```
<데이터 루트>/assets-override/
    portal.js
    portal.css
```

2초 안에 반영된다. 되돌리려면 **파일을 지우면 된다.** 폴더가 없는 것이 평소 상태다.

로그(`Assets` 분류)에 무엇이 걸렸는지 남는다.

```
[Assets] 자산 2개를 덮어썼어요 [93bfc014]: portal.css, portal.js
[Assets] 자산 덮어쓰기가 없어요. 내장 자산으로 갑니다.
```

브라우저는 **새로고침만 하면** 새 파일을 받는다. 페이지 셸의 `?v=` 가 같이 바뀌기 때문이다.

```
v=bee696ad3a5213be            ← 덮어쓰기 없음
v=bee696ad3a5213be-93bfc014   ← 덮어쓴 내용까지 섞은 값
```

---

## 규칙

**덮어쓸 수 있는 이름은 이미 있는 자산의 이름뿐이다.**
`serve_asset` 이 화이트리스트(`mc_assets::get`)로 이름을 먼저 해석하고, **그 이름으로만**
덮어쓰기 표에 묻는다. 폴더에 `secret.txt` 를 넣어도 404 다 — 파일 서버가 아니라 자산 교체다.

| | |
|---|---|
| 덮어쓸 수 있는 것 | `get()` 화이트리스트 12개 + `sw.js` |
| 못 하는 것 | CHANGELOG · `apidoc.html` (내장 문자열이고 새 exe 로만 바뀐다) |
| 파일 하나 상한 | 8MB. 넘으면 그 파일만 건너뛰고 로그에 남는다 |
| 하위 폴더 | 안 본다. 이름이 곧 자산 이름이라 깊이가 있을 이유가 없다 |
| 감시 주기 | 2초. 지문(`이름·크기·수정시각`)이 그대로면 디스크를 안 읽는다 |

---

## 주의

- **임시 수단이다.** 여기 둔 파일은 다음 exe 배포에도 그대로 살아남아 새 내장 자산을
  계속 가린다. 고친 내용을 저장소에 반영하고 배포했으면 **폴더를 비워야 한다.**
- 저장 중인 파일을 읽다 실패하면 그 파일만 건너뛴다. 다음 폴링에서 지문이 또 바뀌므로
  자연히 다시 읽는다.
- 서비스워커(`sw.js`)도 덮어쓸 수 있지만, 서비스워커는 브라우저가 자기 주기로 갱신하므로
  즉시 반영되지 않을 수 있다.

## 검증

`cargo test` — `web::asset_override` 5건 + `web::assets` 배선 1건.

배선 테스트(`an_override_reaches_the_response_and_moves_the_version`)가 중요하다.
모듈 단위 테스트는 "파일을 잘 읽는가" 만 보므로, `serve_asset` 이 그 표를 안 보게
배선을 지워도 전부 초록이다. 실제로 `body_for` 를 내장 바이트만 돌려주게 고쳐 보고
그 테스트만 빨개지는 것을 확인했다.

실서버와 같은 경로로도 확인했다(`scripts\Dev-Local.ps1`):
파일을 떨어뜨리자 봇을 안 끈 채로 응답 바이트와 `?v=` 가 같이 바뀌었고,
`secret.txt` 는 404 였으며, 파일을 지우자 내장 자산과 `?v=` 가 그대로 돌아왔다.
