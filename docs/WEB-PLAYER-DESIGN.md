# 웹 재생기 모드 설계안

작성: 2026-08-09 · 상태: **제안. 아직 구현 없음**

> "그냥 웹 노래 재생기로도 쓸 수 있으면 좋겠다"

봇이 음성 채널에 없어도 리모컨만으로 음악을 듣게 하자는 것. 이 문서는 무엇을
바꿔야 하는지와 그 대가를 적는다. **결정이 필요한 항목은 마지막 절에 모아 뒀다.**

---

## 지금은 왜 안 되나

조작 잠금은 v4.7 에서 풀렸다(`봇이 음성 채널에 있어야만 조작` 을 끄면 버튼이 열린다).
그런데 **소리가 안 난다.** 이유는 하나다.

`웹에서 듣기` 는 자기가 재생을 주관하지 않는다. **봇이 정한 시각표를 따라갈 뿐이다.**

```
서버(코디네이터)  ──> schedule { startedUtc }  ──> 브라우저
                                                   position = now - startedUtc
                                                   유튜브/사운드클라우드 iframe 을 그 위치로 seek
```

`webTargetPosition()` 이 `clock.startedAt()` 을 읽고, 그 값의 출처는 서버의
`schedule.startedUtc` 다. 그런데 시각표를 만드는 `Coordinator::sync_guild` 는 이렇게
시작한다.

```rust
// 음성 채널 미바인딩 → 송출 중지.
let Some(channel_id) = state.voice_channel_id else {
    self.cancel_current(guild_id).await;
    return;
};
```

봇이 음성에 없으면 시각표가 **아예 안 생긴다.** 따라갈 대상이 없으니 브라우저는 조용하다.
대기열도 안 넘어간다 — 다음 곡으로 넘기는 것은 songbird 의 트랙 종료 이벤트이고,
그것도 음성 연결이 있어야 나온다.

즉 막힌 곳은 UI 가 아니라 **"재생을 누가 주관하는가"** 다.

---

## 선택지 셋

### A. 서버가 가상 재생을 돈다 (권장)

코디네이터가 음성 연결 없이도 시각표를 만든다. 오디오는 안 나르고 **시간만 흐른다.**
곡 길이만큼 지나면 타이머가 다음 곡으로 넘긴다.

```
서버: startedUtc 를 찍는다 → 길이만큼 뒤에 advance()
브라우저 여럿: 전부 같은 startedUtc 를 따라간다 → 같은 곡, 같은 위치
봇이 나중에 들어오면: 이미 도는 시각표에 오디오만 붙는다
```

- **모두가 같은 것을 같은 순간에 듣는다.** 이 제품의 정체성이 그것이다.
- 대기열·투표·채팅·통계·차트가 **전부 지금 그대로** 동작한다. 이것들은 시각표가
  존재한다는 것만 전제하지, 봇이 소리를 내는지는 모른다.
- 봇 합류/이탈이 매끄럽다. 시각표는 하나고 오디오만 붙었다 떨어진다.
- 대가: 코디네이터에 songbird 아닌 두 번째 구동기가 생긴다. 아래 "위험" 참고.

### B. 브라우저가 주관한다

브라우저가 곡이 끝나면 서버에 "다음 곡" 을 알린다.

- 서버 변경이 적다.
- 그런데 **듣는 사람이 둘이면 누가 넘기는가.** 둘 다 넘기면 한 곡이 건너뛰어진다.
  탭을 닫으면 대기열이 그 자리에 멈춘다. 사람마다 위치가 달라져 "같이 듣기" 가 깨진다.
- 신뢰할 수 없는 클라이언트에게 대기열 진행 권한을 준다는 점도 걸린다.

### C. 개인 재생기 (서버 상태 없음)

리모컨이 대기열 목록만 읽어 **자기 브라우저에서만** 순서대로 튼다.

- 가장 싸다. 서버는 한 줄도 안 바뀐다.
- 대신 사람마다 다른 곡이 나온다. 대기열·투표·채팅과 무관해진다.
  "웹 재생기" 라는 말에는 맞지만 "같이 듣는 봇" 과는 다른 물건이 된다.

**A 를 권한다.** 클라이언트 전체가 이미 "시각표 하나를 모두가 따라간다" 를 전제로 짜여
있어서, A 는 그 전제를 지키는 유일한 선택이다. B·C 는 그 전제를 깨고 화면 곳곳에서
어긋나기 시작한다.

---

## A 를 하면 무엇을 건드리나

| 자리 | 할 일 |
|---|---|
| `Coordinator::sync_guild` | 음성 미바인딩일 때 곧장 `return` 하지 않고, 가상 구동기로 넘긴다 |
| `Coordinator` (신규) | 곡 길이만큼 뒤에 `advance()` 를 부르는 타이머. 일시정지·이동 시 다시 잡는다 |
| `player/side_effects.rs` | 트랙 시작 훅(프리페치·자동추천·알림)을 가상 재생에서도 태운다 |
| `web/remote.rs` `control` | 일시정지·이동·스킵이 가상 시각표에도 먹게 한다 |
| `stats.rs` | `played` 를 셀지 결정한다(아래 결정 항목) |

**새 API 는 없어도 된다.** 브라우저는 이미 `schedule.startedUtc` 를 보고 있어서,
서버가 시각표를 만들어 주기만 하면 화면은 고칠 게 거의 없다. 이게 A 의 가장 큰 장점이다.

---

## 위험과 대비

**1. 아무도 안 듣는데 대기열이 계속 돈다.** 제일 위험하다. 자동 재생까지 켜져 있으면
봇도 사람도 없는 서버에서 추천이 무한히 돌며 yt-dlp 를 태운다.

> 대비: 가상 재생은 **그 길드에 리모컨 접속자가 있을 때만** 돈다. 접속자 추적은 이미
> 있다(`WebState::presence`, 접속/이탈이 실시간으로 들어온다). 마지막 사람이 나가면
> 시각표를 멈춘다. 다시 들어오면 멈춘 지점부터 잇는다.

**2. 곡 길이를 모르면 언제 넘길지 모른다.** `TrackRef::duration` 은 `Option` 이다.
실제로 `seek` 핸들러도 `unwrap_or(0.0)` 으로 방어하고 있다.

> 대비: 가상 재생을 시작하기 전에 메타데이터를 먼저 확보한다. 길이를 끝내 못 얻으면
> 그 곡은 가상 재생 대상에서 빼고 이유를 남긴다 — **길이를 0 으로 두면 곡이 즉시
> 끝난 것으로 처리돼 대기열이 순식간에 비워진다.**

**3. 시각표가 두 벌이 된다.** 봇이 들어오는 순간 songbird 구동기와 가상 구동기가 같은
길드를 동시에 몰 수 있다.

> 대비: 길드마다 구동기는 **정확히 하나**. 봇이 붙으면 가상 구동기를 먼저 끄고
> 넘겨받는다. 이 인수인계가 이 작업에서 제일 버그가 나기 쉬운 지점이다.

**4. 브라우저 자동재생 정책.** 새로고침 뒤에는 사용자가 한 번 눌러야 소리가 난다.
이미 `webWanted`/`webOn` 으로 갈라 두었으니 그 구조를 그대로 쓴다.

**5. 모바일 백그라운드 재생은 여전히 안 된다.** 유튜브·사운드클라우드 임베드가 정책으로
막는다. 이 설계로도 안 풀린다. 풀려면 서버가 오디오를 직접 흘려야 하는데, 그건
"서버는 오디오를 한 바이트도 나르지 않는다" 는 현재 계약을 뒤집는 별개의 결정이다.

---

## 결정이 필요한 것

1. **언제 켜지나.** 서버 설정으로 명시적으로 켜나(`웹 재생기 모드`), 아니면
   `봇이 음성 채널에 있어야만 조작` 이 꺼져 있고 봇이 없을 때 자동으로 켜지나?
   → 명시적 설정을 권한다. 자동이면 "봇을 잠깐 뺐을 뿐인데 왜 혼자 돌지" 가 된다.

2. **통계에 넣나.** 아무도 실제로 안 들었을 수도 있는 재생을 `played` 로 셀 것인가.
   차트에도 반영되는 값이라 영향이 있다.
   → 세되 **가상 재생 여부를 같이 남기는** 쪽을 권한다. 나중에 갈라 볼 수 있다.

3. **디스코드 알림.** 가상 재생에서도 `지금 재생 중` 카드를 채널에 띄우나?
   → 띄우지 않는 쪽을 권한다. 음성 채널에 아무도 없는데 채널만 시끄러워진다.

4. **범위.** 봇이 아예 없는 서버에서도 리모컨만으로 쓰게 할 것인가, 아니면 봇이 있는
   서버의 보조 수단으로 둘 것인가. 전자면 초대·승인 흐름까지 손대야 한다.

---

## 규모 감각

`sync_guild` 와 코디네이터 구동기 부분이 이 저장소에서 제일 예민한 코드다.
"곡이 안 넘어감", "무음인데 초록불", "두 번 재생" 같은 회귀가 나오기 쉬운 자리이고,
실제로 그런 사고가 이미 여러 번 났다(HANDOFF 의 `.or(player_channel)` 항목, v4.4 의
"자연 종료가 안 넘어가던" 회귀).

그래서 **지금까지 한 UI 수정들과는 성격이 다르다.** 최소 구현이라도 코디네이터를
건드려야 하고, 테스트로 덮지 않으면 조용히 깨진다. 착수 전에 위 결정 4개를 먼저
확정하는 편이 낫다.
